# 2026-08-18 TODO 절단 개수를 고정 개수로 — 임계값이 후보를 거르지 않는다

`report-todo-tuning.md` §4(threshold `+20` 상향)의 **직접 후속**이다. 상향만으로는
해결되지 않은 것이 남아 있었다.

## 1. 문제

`AVOID` 3 + `DO` 5는 **상한**이었다. 매칭이 `예보 점수 ≤ threshold`라
컨디션이 좋은 날에는 만족하는 후보가 5개에 못 미쳐 `DO`가 4개, 때로는 0개로 내려갔다.

**증상은 "빈 화면"이 아니라 "칸 수가 날마다 다름"이다.** 2026-08-17 상향으로
0개인 날은 크게 줄었지만, 4개인 날은 그대로 남았다. 화면이 5칸을 전제로 그리는데
서버가 4개를 주면 그 차이가 그대로 노출된다.

## 2. 검토한 선택지

| # | 안 | 버린 이유 |
|---|---|---|
| ① | threshold를 한 번 더 올린다 (`+20` → `+40`) | **같은 문제가 또 온다.** 계속 올리면 결국 전 행이 `100`이 되고, 그 시점에 `threshold` 컬럼은 아무 의미도 없는 값이 된다. 지금 고치는 게 아니라 미루는 것 |
| ② | 시드 행을 늘린다 (24행 → 40행) | 후보 풀이 커져도 **임계값을 만족하는 후보 수는 그날 예보에 달려 있다.** 컨디션이 좋은 날엔 여전히 0개일 수 있다. 콘텐츠 작성 비용만 늘고 원인은 그대로 |
| ③ | 부족분을 임의로 채운다 (`id` 순·랜덤) | 채우는 순서에 근거가 없다. **이미 우선순위 식이 있는데 쓰지 않는 것** |
| ④ | **임계값을 정렬 1순위로 내린다** ✅ | 아래 |

## 3. 결정

**`TodoScoringPolicy.selectTop`이 두 갈래로 채운다.**

```
1) 예보 점수 ≤ threshold 인 후보  → 우선순위순
2) 모자란 만큼, 나머지 후보       → 우선순위순
3) 앞에서 limit 개 절단
```

우선순위 식(`impact_score × (100 − 예보 점수) + verdictBonus`)도 `impact_score`도
응답 스키마도 건드리지 않았다. **바뀐 것은 "거른다 → 앞세운다" 하나다.**

- **임계값의 의미가 살아남는다.** ①과 달리 값이 여전히 일을 한다 — 이제
  "뜰지 말지"가 아니라 **"먼저 뜰지"**를 정한다. 만족하는 항목은 우선순위 점수가
  낮아도 미만족 항목보다 항상 앞선다(두 갈래를 각각 정렬한 뒤 이어 붙이므로
  갈래를 넘는 역전이 없다)
- **`+20` 상향은 되돌리지 않는다.** 선발 순서를 정하는 값으로 그대로 유효하고,
  `action_master_raise_threshold.sql` 운영 실행도 여전히 필요하다.
  **다만 실행 여부가 화면으로는 안 보이게 됐다** — 개수는 어느 쪽이든 채워지고
  순서만 달라진다 (workflow.md §8에 이 주의를 적어 뒀다)
- **`AVOID`도 같은 규칙을 받는다.** `selectTop`이 카테고리 공용이라 자연히 적용되고,
  AVOID도 같은 이유로 3개 미만이 되던 문제가 함께 풀린다

## 4. 남은 부족 경로 — 하나뿐이다

**그날 예보가 `null`인 지표를 겨냥한 후보는 여전히 빠진다.** 비교할 점수가 없으면
우선순위 자체를 계산할 수 없기 때문이고, 이건 채우기의 문제가 아니다.

`complexion`·`barrier`가 둘 다 `null`인 날에는 `DARK_CIRCLE` 후보 4개만 남아
`DO`가 4개가 된다. 그래서:

- **`AVAILABLE` + 빈 배열 상태를 없애지 않았다.** 드물어졌을 뿐 사라지지 않았고,
  앱은 이 분기를 계속 갖고 있어야 한다
- **앱은 배열 길이로 그린다.** 8개를 가정하고 칸을 고정하면 이 날 깨진다

## 5. 지키는 테스트

| 테스트 | 무엇을 붙든다 |
|---|---|
| `TodoScoringPolicyTest.모자라면_임계값_미만족으로_채운다` | 부족분이 우선순위순으로 채워진다 |
| `TodoScoringPolicyTest.임계값을_만족하는_것이_먼저다` | 미달 쪽 우선순위가 더 높아도 뒤로 밀린다 |
| `TodoScoringPolicyTest.경계값은_포함이다` | 경계값이 만족 갈래에 붙는다 (이제 순서로 확인한다) |
| `TodoServiceTest.컨디션이_좋은_날에도_개수를_채운다` | 예보가 전부 좋아도 `AVOID` 3 + `DO` 5 |
| `TodoScoringPolicyTest.후보가_없으면_비어_있다` | **남은 빈 상태는 예보 `null` 경로뿐** |

앞의 셋은 원래 "임계값이 거른다"를 단언하던 테스트였다. **의미를 바꿔 살렸고
지우지 않았다** — 임계값이 무시되는 방향으로 되돌아가면 이 테스트들이 잡는다.
