## 1. 제품 개요

### 한 줄 정의

애플워치가 기록한 **수면 데이터를 '피부 언어'로 번역**해, 오늘의 피부 상태를 예보하고 셀피로 검증하며, 검증 결과로 개인 모델을 학습시키는 모바일 서비스.

### 핵심 가치 제안

기존 피부 앱은 "지금 피부가 어떤가"를 보여주지만, sleep2skin은 **"어젯밤 수면 때문에 오늘 피부가 어떻게 될 것인가"를 미리 알려주고, 그 예보가 맞았는지 사용자가 직접 검증**한다. 검증이 쌓일수록 예보가 개인화된다.

### 핵심 루프

```
① 수면 수집        앱이 HealthKit에서 읽어 서버로 전달 (앱 시작 시)
      ↓
② 피부 예보        수면 지표 × 개인 가중치 → 피부 지표 3종 0~100 점수
      ↓
③ 행동 처방        예보 기반으로 "오늘 할 것 / 피할 것" 추천 (TODO)
      ↓
④ 셀피 검증        5초 셀피 → LLM Vision 실측 → 예보 vs 실측 대조 → 적중률
      ↓
⑤ 개인 모델 학습    오차 방향·크기로 개인 가중치 보정 → ②의 정확도 상승
      ↓
⑥ 리포트           일간·주간·월간·종합으로 누적 패턴 제시, 필요 시 클리닉 연결
```

이 루프의 **②③④⑤가 전부 서버 로직**이며, 이 백엔드 프로젝트의 실질적 범위다.

### 피부 지표 3종 (확정)

예보(HOME-03)와 실측(HOME-06)은 HOME-07에서 1:1 대조되므로 **반드시 동일한 세트**를 사용한다.

| UI 표시명 | enum | 100점에 가까울수록 | 주 영향 수면 요인 |
|---|---|---|---|
| **다크서클 회복** | `DARK_CIRCLE` | 눈 밑이 **맑다** (어두움이 적다) | 야간 각성 횟수, 총 수면 시간 |
| **혈색** | `COMPLEXION` | 안색에 **생기가 돈다** | HRV·안정시 심박, 취침 규칙성 |
| **장벽** | `BARRIER` | 피부 장벽이 **튼튼하다** | 깊은 수면·REM 시간 |

모든 지표는 **0~100 점수**로 정규화하며, **점수가 높을수록 좋은 상태다.** 세 지표 모두 예외 없이 같은 방향이다.

**`DARK_CIRCLE`은 "다크서클이 심한 정도"가 아니라 "회복된 정도"다.** 이름만 보면 반대로 읽히기 쉬워 UI 표시명을 **"다크서클 회복"**으로 둔다. 각성이 많은 밤일수록 이 점수는 **내려간다**.

> **이 방향은 예보와 실측 양쪽에 똑같이 적용된다.** 한쪽만 뒤집히면 HOME-07 대조가 통째로 무의미해지고, 개인 가중치가 반대 방향으로 학습된다. LLM Vision 프롬프트에도 명시한다 → [architecture.md](architecture.md) §OpenAI Vision

> **"주 영향 수면 요인" 매핑도 2026-08-07에 확정됐다.** 피처 7종의 정확한 정의와 근거는 §10.3, 점수 산출 공식은 §10.4 참조.

### MVP 전제 — 수면 데이터는 완전하게 수신된다 (2026-08-07 확정)

**MVP 범위에서는 앱이 보내는 수면 데이터에 누락이 없다고 가정한다.** 사용자가 애플워치를 착용하고 잤고, 수면 단계(깊은수면·REM·코어)와 HRV·안정시 심박이 모두 기록된 상태로 온다고 본다.

**전제는 "이런 일이 흔치 않다"는 범위 결정이지, "일어나면 무시한다"가 아니다.** 워치 미착용은 실제로 흔하고 데모 중에도 일어날 수 있어, **전제가 깨져도 틀린 값이 나가지 않게** 스코어링을 짰다.

| 전제가 깨지는 경우 | 처리 | 어디에 |
|---|---|---|
| **단계가 일부만 잡힘** | 비율의 분모를 `총 수면`이 아니라 **`깊은수면 + REM + 코어`** 로 잡는다. 측정된 구간만 보므로 비율이 자동으로 맞는다 | §10.5 |
| **단계가 하나도 안 잡힘** | 단계 합이 `0` → **장벽만 빈 상태**로 응답. 0점("위험")으로 내보내지 않는다 | §10.6 |

**둘 다 비용이 0이다.** 스키마 변경도 앱 계약 변경도 없고, **전제가 지켜지면 결과가 완전히 같다**(`deep+rem+core == total`이므로).

**대신 페이로드 규격에 조건이 하나 붙는다** — 단계 미상 구간을 **`core`에 합쳐 보내면 안 된다.** `total`에는 포함하되 단계별 분에는 넣지 않는다. 그래야 `total − (deep+rem+core)`가 미상 구간의 길이가 된다. 이 규격은 우리가 정의해 앱 팀에 통보한다.

**MVP 이후 과제로 남기는 것** — 신뢰할 수 있는 최소 단계 비율. 420분 중 45분만 잡힌 밤의 비율을 그대로 믿을지, 어느 선 아래면 결측으로 볼지는 정하지 않았다.

**보류하지 않는 것** — §10.6의 결측 재정규화는 이 전제와 무관하게 **그대로 필요하다.** 취침 규칙성은 최근 7일 이력을 요구하므로, 데이터가 아무리 완전해도 **신규 사용자는 3일 미만 분기를 반드시 탄다.**

**빈 상태(§7 E)도 이 전제로 줄지 않는다.** 빈 화면은 데이터가 나빠서가 아니라 **사용자가 새로워서** 생긴다 — 첫 업로드 전, 기록 7일 미만, 전일 값 없음은 시간이 지나야만 해소된다.

### 셀피 이미지 취급 정책 (제품 정체성)

셀피는 **분석 직후 즉시 삭제**하며, 얼굴을 복원할 수 있는 어떤 데이터도 보관하지 않는다. 지표 3종의 숫자만 RDS에 남는다. 이 정책은 온보딩(ONB-04)에서 고지되고 마이페이지(MY-04)에서 실제 실행 지점을 제공하는, **마케팅 문구가 아니라 구현 제약**이다.

> ⚠️ **정확한 표현 주의**: 이미지를 파일로 어디에도 쓰지 않지만, 처리 중 서버 메모리를 거치고 OpenAI로 전송된다. 따라서 "저장하지 않습니다"가 아니라 **"분석 직후 즉시 삭제하며, 얼굴을 복원할 수 있는 데이터를 보관하지 않습니다"**로 표현해야 한다. 이를 뒷받침하는 구현은 §5.2 참조.

#### 고지 문구 원칙 (B4 — 2026-08-07 확정)

**외부 AI로 전송되어 분석된다는 사실을 명시한다.** 사용자가 "내 얼굴 사진이 어디로 가는가"를 알고 동의하게 하는 것이 이 고지의 목적이다.

| 쓸 수 있는 문장 | 근거 |
|---|---|
| "분석을 위해 **외부 AI(OpenAI)로 이미지가 전송**됩니다" | 우리가 하는 일이므로 확실하다 |
| "**서버에 저장하지 않습니다**" — 우리 인프라 한정 | 엔티티에 이미지 컬럼이 없어 저장할 곳 자체가 없다 |
| "분석 직후 즉시 삭제하며, **얼굴을 복원할 수 있는 데이터를 보관하지 않습니다**" | 지표 3종의 숫자만 남는다 |

| 쓰면 안 되는 문장 | 이유 |
|---|---|
| "어디에도 저장되지 않습니다" | **제공자 쪽 보관 여부를 우리가 모른다.** 확인되지 않은 프라이버시 주장이다 |
| "OpenAI도 보관하지 않습니다" | 위와 같다. 확인 전까지 쓸 수 없다 |

**주어를 생략하지 않는 것이 핵심이다.** "저장하지 않습니다"는 주어가 없어 "아무도 저장하지 않는다"로 읽힌다. **"서버에"를 붙이면 참이고, 빼면 확인되지 않은 주장이 된다.**

> 이렇게 정하면 **OpenAI 보관 정책 확인(B4) 없이도 문구를 확정할 수 있다.** 확인이 끝나 "제공자도 보관하지 않는다"가 사실로 밝혀지면 그때 문장을 **추가**하면 되고, 그전까지는 없어도 고지가 성립한다.
>
> 적용 지점: 온보딩 ONB-04 · 마이페이지 MY-04 · 셀피 분석 직전 화면(HOME-05)

### 온보딩 플로우

```
시작 화면(ONB-01)
   ↓
개인정보 동의(ONB-02) ──no──→ 앱 종료
   │ yes
   ↓
수면 데이터 연결(ONB-03) ──yes/no 모두──→ 랜딩 HOME(ONB-05)
```

> 미연결 사용자도 HOME에 진입하므로 **HOME-02·HOME-03의 빈 상태 처리가 필수**다. (§7 참조)

### 화면 도메인 ↔ 백엔드 패키지 매핑

화면 도메인과 백엔드 데이터 도메인은 1:1이 아니다. HOME 화면 하나가 수면·피부 두 데이터 도메인을 걸친다.

| 화면 도메인 | 백엔드 패키지 | 근거 |
|---|---|---|
| ONBOARDING | `user` | 동의 이력, 온보딩 완료 상태 |
| HOME | `sleep` + `skin` | 수면 통역(HOME-02)은 sleep, 예보·검증·학습(HOME-03/06/07/08)은 skin |
| TODO | `todo` | 추천 엔진, 체크리스트 |
| REPORT | `report` | 집계·분석 전용 (sleep·skin 조회) |
| MY | `user` | 프로필, 데이터 관리 |

상세는 [architecture.md](architecture.md) 참조.

## 4. 기능 명세

우선순위: `high` = MVP 필수 / `medium` = 데모 품질 향상 / `low` = 후순위
난이도: 명세서의 개발 난이도(상·중·하)
BE: 서버 작업 유무 — **`—` 표시는 클라이언트 전용, 백엔드 구현 대상 아님**

### 4.1 온보딩 (ONB)

| ID | 기능명 | 우선 | 난이도 | 백엔드 처리 |
|---|---|---|---|---|
| ONB-01 | 앱 시작 화면 (가치 제안) | high | 하 | 화면은 클라이언트 전용. **진입 분기 근거는 `GET /users/me`가 제공** (아래 참조) |
| ONB-02 | 개인정보 수집·이용 동의 (분기) | high | 하 | 동의 이력 저장(약관 버전·동의 시각·사용자 식별자) |
| ONB-03 | 수면 데이터 연결 (HealthKit) | high | 중 | **앱이 전달한 수면 세션 수신 → 정규화 → DB 저장** |
| ONB-04 | 프라이버시 고지 (셀피 처리 방식) | high | 하 | — (정적 화면). 문구는 §2 고지 문구 원칙을 따른다 — **AI 전송 사실을 명시**하고, 미저장은 "서버에" 한정으로 쓴다 |
| ONB-05 | 랜딩 진입 및 온보딩 완료 처리 | high | 하 | 온보딩 완료 상태 및 초기 설정 저장 |

> **ONB-03 난이도 하향** (상→중): 서버가 HealthKit에 직접 접근하지 않고 앱이 읽어 전달하는 구조로 확정되어, 서버는 수신·정규화·저장만 담당한다.

> **ONB-01 진입 분기를 서버 조회로 바꿨다** (2026-08-10). 원래는 앱의 로컬 온보딩 완료 플래그만 확인할 계획이었다. 그런데 **로컬 플래그로는 약관 개정에 따른 재동의를 감지할 수 없다** — 앱은 "동의 완료"만 기억하고 있어 `CURRENT_TERMS_VERSION`이 올라간 것을 영원히 모른다. `consent_history`를 이력 테이블로 유지한 목적([erd.md](erd.md) §3.2)이 실현되지 않는다. 앱은 시작 시 `GET /api/v1/users/me`를 호출해 `consentAgreed`·`onboardingCompleted` 두 값으로 분기한다 ([api.md](api.md) §2.1). 화면 자체는 여전히 클라이언트 전용이다.

**수집 데이터 5종** (앱이 HealthKit에서 읽기 전용으로 취득 후 전달):

| 수면 데이터 | 피부 측면의 의미 | 연결 지표 |
|---|---|---|
| ① 깊은 수면·REM·코어 (분) | 장벽 재생 / 콜라겐 지표 | `BARRIER` (코어는 피처 아님) |
| ② **잠든** 시각 · 기상 시각 | 수면 규칙성 | `COMPLEXION` (기상 시각은 피처 아님) |
| ③ 야간 각성 횟수 | **다크서클 예측의 핵심 변수** | `DARK_CIRCLE` |
| ④ HRV · 안정시 심박 | 스트레스성 트러블 신호 | `COMPLEXION` |
| ⑤ 각성 총 시간 (분) | 각성의 길이 — 횟수만으로는 안 잡히는 축 | **표시 전용** — 피처 아님 (§10.3) |

**③⑤의 각성 판정 기준 — 5분** (2026-08-06 확정, §7 B5). **5분 이상 지속된 `AWAKE` 구간만** 각성 1회로 세고, 총 시간도 **그 구간들만** 합산한다. 5분 미만은 뒤척임으로 보고 버린다. 임계값이 없으면 30초 뒤척임까지 세어 각성 횟수가 사람마다 20회씩 나온다.

- **③과 ⑤에 같은 임계값을 쓴다.** REP-04가 둘을 나란히 보여주므로, 횟수에만 걸면 "각성 0회 · 총 12분" 같은 모순이 화면에 나온다
- **마지막 `asleep` 이후의 `AWAKE`는 제외한다.** 그건 야간 각성이 아니라 기상이다. 세면 모든 사용자가 매일 최소 1회를 깔고 시작해 다크서클 예보가 전반적으로 눌린다
- **서버가 단계 구간에서 계산한다.** 앱이 보낸 각성 횟수를 그대로 받지 않는다 — 임계값이 서버 상수여야 앱 배포 없이 바꿀 수 있고 전 사용자에게 같은 기준이 적용된다. → [erd.md](erd.md) §3.3

> 수집 데이터 5종과 **연결 지표 매핑 모두 확정**이다. 매핑의 출처는 §10.3. **⑤는 2026-08-06 추가되어 2026-08-07에 표시 전용으로 확정됐다.**

#### 수면 세션의 경계 — 첫 기상까지 (2026-08-07 확정, §7 E8)

**낮잠은 수면 세션에 넣지 않는다.** 기상한 뒤 다시 잠든 것은 별개의 수면이며 예보 산출에 쓰지 않는다. 하루에 여러 수면이 기록돼도 **첫 수면만** `sleep_session` 한 행이 된다.

그래서 **"야간 각성"과 "기상"을 가르는 기준**이 필요하다. **연속 `AWAKE` 60분**이다.

| 연속 `AWAKE` 길이 | 판정 | 처리 |
|---|---|---|
| 5분 미만 | 뒤척임 | 버린다 — 횟수·총 시간 모두 미반영 |
| 5분 이상 ~ 60분 미만 | **야간 각성** | 각성 1회로 세고 총 시간에 합산 |
| **60분 이상** | **기상** | **거기서 세션을 끊는다.** 이후 구간은 낮잠으로 보고 버린다 |

- **60분 임계값이 없으면 `AWAKE_COUNT`가 항상 0이 된다.** "첫 기상까지"를 문자 그대로 구현하면 5분짜리 각성에서도 세션이 끊겨, **세션 안에 5분 이상 각성이 존재할 수 없다.** 값 범위는 0~100 정상이라 어떤 제약에도 안 걸리고 다크서클 적중률만 조용히 무너진다 — `DARK_CIRCLE` 방향 뒤집힘과 같은 종류의 함정이다
- **`wake_time`은 첫 기상 시각이다.** 60분 이상 `AWAKE`가 시작되는 시점과 마지막 `asleep`이 끝나는 시점 중 **앞선 쪽**이다
- **서버가 판단한다.** 앱이 세션을 어떻게 쪼개 보내든 서버가 단계 구간에서 다시 계산한다. 앱의 분할을 그대로 믿으면 기기·OS 버전별로 기준이 달라 사용자마다 각성 횟수가 들쭉날쭉해진다
- 두 임계값(5분·60분)은 **`domain/sleep`의 정규화 정책 상수**다 — `ScoringPolicy`가 아니다. 스코어링 파라미터가 아니라 **수집 정규화 규칙**이기 때문이다 ([erd.md](erd.md) §3.3). 서버 상수이므로 앱 배포 없이 조정할 수 있다

**스코어링 근거와도 맞는 방향이다.** §10.5가 인용하는 참조값(권장 수면 7~9시간, N3 13~23%, REM 18~27%)은 전부 **야간 수면 기준**이다. 낮잠을 합산하면 오히려 문헌과 어긋난다.

> ⚠️ **한계** — 새벽에 60분 이상 깨어 있다가 다시 자는 사용자는 **총 수면 시간이 실제보다 짧게 기록된다.** 불면 경향이 있으면 실제로 발생한다. 60분은 이 위험과 "각성 횟수가 0으로 깎이는" 반대 위험 사이의 절충이며, 서버 상수라 운영 데이터가 쌓이면 조정한다.

**수집 세트와 표시 세트는 다르다.** 사용자에게 보여주는 것은 REP-04의 **4종**이고, 나머지는 화면에 나오지 않지만 예보 산출에 쓰인다.

**수집 · 피처 · 표시는 서로 다른 세 층위다.** "저장한다"가 "스코어링에 쓴다"를 뜻하지 않는다.

| 항목 | 수집·저장 | **스코어링 피처** | 표시 (REP-04) |
|---|:---:|:---:|:---:|
| 총 수면 시간 | ✓ | `TOTAL_SLEEP` | ✓ |
| 깊은 수면 | ✓ | `DEEP_SLEEP` (비율) | ✓ |
| REM | ✓ | `REM_SLEEP` (비율) | — |
| 코어 | ✓ | — | — |
| 각성 횟수 | ✓ | `AWAKE_COUNT` | ✓ |
| 각성 총 시간 | ✓ | — (표시 전용, §10.3) | ✓ |
| 잠든 시각 | ✓ | `BEDTIME_REGULARITY`로 파생 | — |
| 기상 시각 | ✓ | — | — |
| HRV | ✓ | `HRV` | — |
| 안정시 심박 | ✓ | `RESTING_HEART_RATE` | — |

**수집 10항목 · 피처 7종 · 표시 4종.** 피처 목록의 확정 근거는 §10.3에 있다.

**`DEEP_SLEEP`·`REM_SLEEP`은 분이 아니라 비율로 스코어링하고, 분모는 `깊은수면 + REM + 코어`다** (§10.5). 저장은 분 단위 그대로이고, 비율은 스코어링 시점에 계산한다 — 컬럼을 늘리지 않는다.

**피처가 아닌 것도 버리지 않는다.** 코어는 `asleepUnspecified` 때문에 단계 합이 총 수면과 안 맞는 경우를 확인하는 데 쓰이고([erd.md](erd.md) §3.3), 기상 시각은 총 수면 시간 검증과 화면 표현에 쓰인다. 나중에 피처로 승격할 여지도 남는다.

**②의 기준은 "잠든 시각"(첫 `asleep` 시작)이지 "누운 시각"이 아니다.** 누운 시각은 HealthKit `inBed` 샘플에서만 나오는데 **안 남는 밤이 생긴다.** 두 기준을 섞어 규칙성을 재면 규칙적으로 자는 사용자도 편차가 크게 나와 혈색 예보만 나빠진다.

**그래서 `inBed`에 의존하는 지표는 수집·표시 양쪽에서 제외했다** — 누운 시각 · 누운 시간 · **입면 지연** · **수면 효율**. 넷 다 함께 결측되므로 피처로 쓰면 스코어링에 결측 분기가 생긴다. → [erd.md](erd.md) §3.3

### 5.1 수면 데이터 수신 (HealthKit)

서버는 HealthKit에 직접 접근할 수 없다. 앱이 권한을 얻어 읽은 데이터를 서버로 전달한다.

```
[앱 시작]
  → 앱이 HealthKit에서 지난밤 수면 세션 읽기
  → POST /api/v1/sleep/sessions  (수면 세션 페이로드)
  → 서버: [중복 판단] → 정규화 → 저장 → 즉시 스코어링(HOME-03) → 예보 응답
  → 앱: HOME 화면에 예보 표시
```

이 구조의 결과:
- **서버 스케줄러가 필요 없다.** 배치 인프라와 실패 재시도 설계가 통째로 사라진다.
- HealthKit 단계 구분이 기기·OS 버전별로 다를 수 있으므로 **앱↔서버 간 수면 단계 매핑 규칙을 계약으로 고정**해야 한다.

#### 중복 수신 차단 (필수)

앱이 시작될 때마다 업로드하므로, **새 수면 데이터가 생기기 전까지는 같은 세션이 반복 전송된다.** 하루에 앱을 다섯 번 켜면 같은 데이터가 다섯 번 온다.

이때 **처리를 시작하기 전에 중복을 판단해 되돌린다.** 저장 후 덮어쓰는 upsert가 아니라, **아예 처리하지 않는다.**

```
POST /api/v1/sleep/sessions 수신
  │
  ├─ 페이로드 정규화 → 내용 해시 계산            ← 저장 전에 수행
  │
  ├─ (user_id, sleep_date)로 기존 세션 조회
  │
  ├─ ① 기존 없음        → 저장 + 스코어링 + 예보 산출    → 201 Created
  ├─ ② 기존 있음·해시 동일 → 아무것도 하지 않음
  │                       → 기존 예보를 그대로 반환      → 200 OK
  └─ ③ 기존 있음·해시 다름 → 그날 검증을 마쳤는가?
                             ├ 검증 완료 → 갱신하지 않음. 기존 예보 반환 (processed=false)
                             └ 검증 전   → 갱신 + 재산출        (processed=true)
```

**②에서 재처리를 막아야 하는 이유** — 단순한 성능 문제가 아니다:

| 이유 | 설명 |
|---|---|
| **검증 무효화 방지** | 예보를 다시 산출하면 오늘자 예보값이 바뀐다. 이미 셀피 검증(HOME-07)을 마쳤다면 **대조 기준이 사후에 바뀌어 적중률이 조작된 셈**이 된다 |
| 학습 오염 방지 | 재산출이 개인 가중치 학습(HOME-08)을 다시 트리거하면 같은 데이터로 여러 번 학습해 가중치가 왜곡된다 |
| 비용 | 스코어링·집계가 무의미하게 반복된다 |

**응답에 처리 여부를 명시한다.** 앱이 "새 예보인지 기존 예보인지"를 알아야 화면 갱신 여부를 판단할 수 있다.

```json
{ "success": true, "data": { "processed": false, "forecast": { ... } } }
```

**구현 요건**:
- `SleepSession`에 `payload_hash` 컬럼(정규화된 페이로드의 SHA-256)을 둔다
- `(user_id, sleep_date)`에 유니크 제약을 걸어 DB 레벨에서도 중복을 막는다
- 해시 계산은 **정규화 후** 수행한다. 앱이 필드 순서를 바꿔 보내도 같은 데이터로 판정되어야 한다

### 5.2 셀피 이미지 파이프라인 (스토리지 없음)

"얼굴 데이터를 보관하지 않는다"를 **설명이 아니라 구조로 증명**하는 것이 목표다. 그래서 **이미지를 저장할 곳 자체를 두지 않는다.**

```
[앱] 셀피 촬영 (갤러리 저장 안 함)
  → POST /api/v1/skin/selfie  (multipart/form-data)
  → 서버: 요청 바이트를 메모리에서 그대로 OpenAI Vision에 전달
           (디스크·버킷에 쓰지 않는다)
  → 지표 3종 0~100 산출
  → RDS에 숫자 지표 3개만 저장
  → 앱에 결과 반환 → 응답이 끝나면 바이트는 참조가 끊긴다
```

**보관하지 않음을 뒷받침하는 구현 장치**:

| # | 장치 | 목적 |
|---|---|---|
| 1 | **오브젝트 스토리지를 쓰지 않음** | 업로드할 버킷이 없으면 잔존 사고도 없다 |
| 2 | **DB 스키마에 이미지 경로/URL 컬럼을 두지 않음** | 애초에 이미지를 참조할 방법이 없다. 스키마 자체가 정책의 증거 |
| 3 | **이미지 바이트를 필드·캐시·정적 변수에 담지 않음** | 요청 처리 범위를 벗어나 살아남지 않는다 |
| 4 | **예외 로그에 바이트·base64를 남기지 않음** | 실패 경로로 이미지가 로그에 새는 것을 막는다 |

> **S3 경유 초안에서 바뀐 부분이다.** 임시 업로드를 없애면서 Lifecycle 만료 정책·`finally` 삭제 블록·버킷 접근제어가 **전부 필요 없어졌다.** 지켜야 할 장치가 4개에서 사실상 2개(장치 1·2)로 줄었고, 정책이 깨질 경로도 그만큼 줄었다.

**확인이 필요한 항목**:
- OpenAI API의 데이터 보관 정책 — 요청 로그에 이미지가 남는지, zero data retention 적용 가능한지 확인 후 사용자 고지 문구를 확정해야 한다. **S3를 뺀 뒤에도 이 항목은 그대로 남는다** — 우리 인프라가 아니라 제공자 쪽 보관의 문제다. (§7 B4)
- 이미지가 메모리를 거치는 것은 변하지 않으므로, 고지 문구는 여전히 "저장하지 않습니다"가 아니라 **"분석 직후 즉시 삭제하며, 얼굴을 복원할 수 있는 데이터를 보관하지 않습니다"**여야 한다.

## 10. 확정된 정책값

§9의 임시값과 달리 **팀 논의로 확정된 값**이다. `ScoringPolicy` 상수로 두는 것은 같지만 재확정 대기 상태가 아니다.

### 10.1 등급 컷오프 (B2 — 2026-08-06 확정)

0~100 예보 점수를 등급 라벨로 매핑한다. **세 지표가 같은 구간을 쓴다.**

| 지수 | 등급 | 의미 |
|---|---|---|
| 0~25 | **위험** | 피부 컨디션 저하 가능성이 높음 |
| 26~50 | **주의** | 피부 컨디션 저하 가능성 있음 |
| 51~75 | **보통** | 일반적인 수준 |
| 76~100 | **안정** | 수면으로 인한 피부 영향이 낮음 |

**25점씩 4등분이라 경계값이 `25`·`50`·`75` 세 개뿐이다.** 지표별로 다른 구간을 두지 않으므로 상수도 세 개면 된다.

> ⚠️ **원본 팀 협의 자료(2026-08-06)는 의미 열이 등급과 역순으로 적혀 있었다** — `0~25`(위험)에 "수면으로 인한 피부 영향이 낮음"이 붙는 식이었다. 자료 상단의 "숫자가 클수록 좋은 것"과 등급 라벨 방향이 서로 일치하므로 **그 둘을 기준으로 삼고 의미 열을 바로잡아 옮겼다.** 위 표가 확정본이다.
> 이 방향이 뒤집히면 값 범위는 정상이라 어떤 검증에도 안 걸리고 **화면 문구만 정반대로 나간다.** `DARK_CIRCLE`과 같은 종류의 함정이다(§4.1).

### 10.2 판정 오차 구간 (B3 — 2026-08-06 확정)

HOME-07 검증에서 `예보 − 실측`을 판정 라벨로 매핑한다. **지표별로 따로 판정하고, 적중률은 3개 중 `적중` 비율이다.**

| 예보 − 실측 | 판정 | 의미 |
|---|---|---|
| ±5점 이내 | **적중** | 예보와 실측이 거의 일치 |
| ±6~15점 | **근접** | 비슷하게 예측 |
| −16점 이하 | **과소예측** | 예보 점수를 실제보다 낮게 냈다 |
| +16점 이상 | **과대예측** | 예보 점수를 실제보다 높게 냈다 |

**"과소/과대"는 점수 축 기준이다.** 점수는 높을수록 좋으므로 **점수를 과소예측한 것은 피부 위험을 과대평가한 것**이다. 두 축이 서로 반대라, 문구를 쓸 때 어느 축인지 밝히지 않으면 뜻이 뒤집힌다 — "위험을 낮게 예측했다"는 `과대예측`을 가리킨다.

**`적중`·`근접`은 절댓값으로, `과소`·`과대`는 부호로 가른다.** `|차이| ≤ 5` → `|차이| ≤ 15`를 먼저 걸고 남은 것만 부호를 본다. 순서를 바꾸면 −5점이 `과소예측`으로 새어 나간다.

### 10.3 수면 피처 → 피부 지표 매핑 (B1 — 2026-08-07 확정)

**이 절이 매핑의 유일한 출처다.** §9.1에 임시로 있던 표가 확정되어 이리로 옮겨졌다. 매핑을 바꿀 땐 여기를 고치고 §4.4 REP-07 표와 [erd.md](erd.md) §3.7을 맞춘다.

**피처 7종.** 이 표의 각 행이 곧 `personal_weight`의 한 행이다.

| # | 수면 피처 | `sleep_feature` | → 지표 | 근거 | 결측 |
|---|---|---|---|---|---|
| 1 | 야간 각성 횟수 | `AWAKE_COUNT` | `DARK_CIRCLE` | 수면 부족 시 눈 밑 어두움·창백함이 관찰자에게 식별되는 대표 신호 (Axelsson 2010, Sundelin 2013) | 없음 |
| 2 | 총 수면 시간 | `TOTAL_SLEEP` | `DARK_CIRCLE` | 위와 같은 계열. 수면 시간 제한이 안면 피로 신호를 만든다 | 없음 |
| 3 | 깊은 수면 시간 | `DEEP_SLEEP` | `BARRIER` | 성장호르몬 분비의 대부분이 첫 서파수면 펄스에서 일어나고 이것이 섬유아세포의 콜라겐 생성을 유도. 수면의 질이 낮은 군은 기저 TEWL이 높고 장벽 회복이 느리다 (Oyetakin-White 2015) | 없음 |
| 4 | REM 수면 시간 | `REM_SLEEP` | `BARRIER` | ⚠️ **직접 근거가 약하다** — 아래 참조 | 없음 |
| 5 | 취침 규칙성 | `BEDTIME_REGULARITY` | `COMPLEXION` | 수면 타이밍 불규칙성이 심혈관·대사 지표와 연관. 혈색은 말초 순환의 표현이다 | 없음 |
| 6 | HRV | `HRV` | `COMPLEXION` | 야간 부교감 활성의 지표. 스트레스 부하가 안색에 드러나는 경로 | **있음** ⚠️ |
| 7 | 안정시 심박 | `RESTING_HEART_RATE` | `COMPLEXION` | 위와 같은 신호원의 반대 축 | **있음** ⚠️ |

지표별 분포: `DARK_CIRCLE` 2 · `COMPLEXION` 3 · `BARRIER` 2

**`REM_SLEEP` → `BARRIER`는 직접 근거가 약하다는 것을 명시해 둔다.** 문헌은 피부 회복을 서파수면 중심으로 설명하고 REM은 기억·학습 쪽 기능으로 갈린다. 그럼에도 포함한 이유는 생리학이 아니라 **학습 가능성**이다 — 피처가 1개뿐인 지표는 개인 가중치가 점수 전체를 같은 비율로 밀 뿐 아무것도 학습하지 못하고(상대 비중을 다툴 상대가 없다), REP-07의 `BARRIER` 상관 강도도 같은 이유로 무의미해진다. **초기 가중치는 `DEEP_SLEEP`과 동률로 두고, 실제 기여도는 개인 가중치 학습이 재조정하게 한다.** 이 한계를 숨기지 않고 문서와 리포트 문구 양쪽에서 같은 태도로 다룬다.

**각성 총 시간(`AWAKE_MINUTES`)은 스코어링 피처가 아니다 — 표시 전용으로 확정.** REP-04에는 계속 나오지만 예보 산출에 넣지 않는다. 이유는 두 가지다:

- **각성 횟수와 같은 구간 집합에서 나온다.** 둘 다 §4.1의 5분 임계값으로 걸러낸 같은 `AWAKE` 구간에서 계산되므로 중복 상관이 강하다. 둘 다 `DARK_CIRCLE`에 붙이면 같은 신호가 두 번 계산된다
- **8행이 되면 학습에 필요한 검증 횟수가 늘어난다.** 개인 가중치가 의미 있게 수렴하려면 행 수만큼 검증 표본이 필요하고, 해커톤 기간의 데모 데이터로는 7행도 빠듯하다

> 배정을 미룬 것이 아니라 **넣지 않기로 정한 것**이다. 나중에 피처로 승격하려면 횟수와 합성해 하나의 "각성 부담" 부분점수로 만드는 쪽을 먼저 검토한다 — 8번째 행을 늘리는 것보다 중복 상관이 깨끗하게 해소된다.

**제외 유지** — 저장은 하지만 피처가 아니다:

| 항목 | 이유 |
|---|---|
| 코어 수면 | `TOTAL_SLEEP`과 강하게 겹친다. 얕은 수면이라 피부 회복과의 직접 연결도 약하다 |
| 기상 시각 | 취침 규칙성은 `sleep_onset_time`으로만 계산한다(§4.1). 기상 시각은 총 수면 시간 검증·화면 표현용 |
| 각성 총 시간 | 위 참조 — 표시 전용 |

### 10.4 가중합 스코어링 공식 (B1 — 2026-08-07 확정)

```
지표점수(m) = Σ_f [ w'(m,f) × s(f) ]          f = 지표 m에 붙은 피처
w'(m,f)    = w일반(m,f) × w개인(m,f) / Σ_f(...)   ← 지표 내 합 = 1로 재정규화
s(f)       = 피처 f의 0~100 부분점수 (§10.5)
```

산출한 값은 **반올림해 정수 0~100**으로 저장하고, 등급 라벨은 저장하지 않고 §10.1로 매번 계산한다.

**이 형태를 고른 이유는 세 가지 성질 때문이다.**

| 성질 | 내용 |
|---|---|
| **0~100이 자동으로 보장된다** | `s`가 0~100이고 `w'`의 합이 1이므로 가중평균의 결과도 0~100이다. "0~100 정규화" 단계에 별도의 스케일 상수나 클램프가 생기지 않는다 |
| **개인 가중치가 상대 비중을 학습한다** | 배수로 곱한 뒤 **재정규화**하므로 한 피처의 가중치를 올리면 같은 지표의 다른 피처 비중이 내려간다. 재정규화가 없으면 점수 전체가 같은 방향으로 밀릴 뿐 학습이 되지 않는다 |
| **결측이 분기 없이 처리된다** | 없는 피처의 항을 빼고 `w'`를 다시 재정규화하면 끝이다. §10.6이 이 성질 위에 서 있다 |

**초기(일반) 가중치는 지표 내 균등이다.**

| 지표 | 피처 | `w일반` |
|---|---|---|
| `DARK_CIRCLE` | `AWAKE_COUNT` · `TOTAL_SLEEP` | 각 `0.5` |
| `COMPLEXION` | `BEDTIME_REGULARITY` · `HRV` · `RESTING_HEART_RATE` | 각 `1/3` |
| `BARRIER` | `DEEP_SLEEP` · `REM_SLEEP` | 각 `0.5` |

**균등에서 출발하는 것이 근거 없는 차등보다 방어하기 쉽다.** 피처별 상대 기여도를 특정할 수 있는 문헌이 피부 지표 3종에 대해 존재하지 않는다. 여기서 `0.4 / 0.35 / 0.25` 같은 숫자를 만들면 그 숫자 자체가 새로운 임시값이 된다. **근거는 가중치가 아니라 정규화 기준(§10.5)에 싣고**, 차등은 개인 가중치 학습(HOME-08)이 데이터로 만들게 한다 — "처음엔 편견 없이 시작해 개인 데이터로 학습한다"가 이 서비스의 컨셉과도 일치한다.

**개인 가중치는 `personal_weight.weight`의 배수값이다.** 행이 없는 사용자(첫 검증 전)는 `1.0`으로 간주하며, 이때 `w'`는 `w일반`과 같다. → [erd.md](erd.md) §3.7

### 10.5 피처 정규화 기준 (B1 — 2026-08-07 확정)

각 피처를 0~100 부분점수 `s(f)`로 바꾼다. **구간선형(piecewise linear)이며, 양 끝은 클램프한다.**

| 피처 | 입력 단위 | 100점 | 0점 | 근거 |
|---|---|---|---|---|
| `TOTAL_SLEEP` | 분 | 420~540 | ≤300 | 성인 권장 수면 7~9시간 (NSF 2015, AASM) |
| `AWAKE_COUNT` | 회 (5분↑) | ≤1 | ≥5 | WASO 정상 20분 미만(50세 미만), 5분 초과 각성이 임상적 분기점 |
| `DEEP_SLEEP` | **단계 합 대비 %** | 13~23 | ≤5 | 건강 성인 N3 비율 정상 범위 (Boulos 2019 메타분석) |
| `REM_SLEEP` | **단계 합 대비 %** | 18~27 | ≤8 | 같은 메타분석의 REM 비율 정상 범위 |
| `BEDTIME_REGULARITY` | 최근 7일 SD (분) | ≤30 | ≥120 | 수면 타이밍 규칙성 합의문(NSF 2023)·UK Biobank SRI |
| `HRV` | 야간 RMSSD (ms) | ≥60 | ≤15 | 웨어러블 야간 RMSSD 참조값 (성인 단일 밴드) |
| `RESTING_HEART_RATE` | 야간 bpm | ≤55 | ≥85 | 야간 안정시 심박 참조값 (성인 단일 밴드) |

**과다 구간도 감점한다.** `TOTAL_SLEEP`은 540분을 넘으면 완만히 내려가고(720분에서 50점), `DEEP_SLEEP`·`REM_SLEEP`도 정상 범위 상단을 넘으면 소폭 감점한다. 권장 범위를 벗어난 것은 양방향 모두 이탈이다.

**깊은수면·REM을 분이 아니라 비율로 잡은 것이 이 설계의 핵심 판단이다.**

- 수면의학 참조값 자체가 **비율**로 정의돼 있다. 분으로 환산하면 출처가 말하지 않은 값을 우리가 만들어내게 된다
- 절대 분으로 하면 6시간 자고 깊은수면 70분인 사람이 9시간 자고 90분인 사람보다 낮게 나온다. **짧고 질 좋은 수면이 구조적으로 불리해진다**
- §9.1이 지적했던 `DEEP_SLEEP`·`REM_SLEEP`과 `TOTAL_SLEEP`의 중복 상관("총 수면이 늘면 함께 는다")이 비율로 바꾸면 상당 부분 빠진다. 승격의 대가로 받아들였던 문제가 정규화 단계에서 해소된다

#### 분모는 `총 수면`이 아니라 `깊은수면 + REM + 코어`다

```
비율(DEEP_SLEEP) = deep_sleep_minutes / (deep + rem + core) × 100
```

**단계가 실제로 판별된 구간만 분모에 넣는다.** 총 수면 시간에는 단계 미상(`asleepUnspecified`) 구간이 섞일 수 있는데, 그걸 분모에 넣으면 **측정하지 못한 시간이 "깊은 수면이 아니었던 시간"으로 계산된다.**

| 상황 | 분모 = 총 수면 | 분모 = 단계 합 |
|---|---|---|
| 단계가 전부 잡힘 (MVP 전제) | `deep+rem+core == total`이므로 **완전히 동일** | 동일 |
| 420분 중 45분만 잡힘 (깊은수면 20 · REM 25) | `20/420 = 4.8%` → **0점** (틀림) | `20/45 = 44%` → 정상 범위 |
| 하나도 안 잡힘 | `0/420 = 0%` → **0점 = "위험"** | 분모가 0 → **빈 상태**(§10.6) |

**전제가 지켜지면 두 방식의 결과가 완전히 같고, 깨지는 순간에만 갈린다.** 스키마 변경도 앱 계약 변경도 없이 계산식만 바꾸면 되므로 **비용이 0이다.**

> ⚠️ **앱 페이로드 규격이 여기에 달려 있다.** 단계 미상 구간을 **`core`에 합쳐 보내면 안 된다** — 합치면 `deep+rem+core == total`이 되어 분모를 바꾼 의미가 사라진다. **`total`에는 포함하되 `deep`·`rem`·`core` 어디에도 넣지 않는다.** 그러면 `total − (deep+rem+core)`가 곧 미상 구간의 길이가 된다 ([erd.md](erd.md) §3.3). 이 규격은 우리가 정의해 앱 팀에 통보한다.

**한계** — 420분 중 45분만 잡힌 밤에서 그 45분의 비율을 전체로 추정하는 것은 표본이 작다. 다만 **5시간을 "깊은 수면 0분"으로 취급하는 것보다는 확실히 낫다.** 신뢰할 수 있는 최소 단계 비율(예: 총 수면의 몇 % 이상 잡혀야 하는가)은 MVP 이후 과제로 남긴다.

**`HRV`·`RESTING_HEART_RATE`는 연령대 구분 없는 단일 성인 밴드를 쓴다.** 문헌상 야간 RMSSD는 20대 55~105ms, 40대 40~75ms로 연령 의존이 크지만 **`users`에 나이 컬럼이 없다**([erd.md](erd.md) §3.1). 컬럼을 추가하는 대신 밴드를 넓게 잡고 개인차는 개인 가중치 학습에 맡긴다 — 개인 baseline 대비 편차로 가면 최근 N일이 쌓이기 전까지 혈색 예보를 낼 수 없어 신규 사용자 빈 상태가 하나 더 늘어난다.

**5분 임계값(§4.1)은 문헌과 일치한다.** 건강한 성인도 밤에 미세각성이 10~30회 일어나지만 대부분 3분 미만이고, 5분을 넘어가는 각성부터 수면 분절의 문제로 다뤄진다. 임의로 고른 값이 아니다.

### 10.6 결측·이력 부족 처리 (B7 — 2026-08-07 확정)

**결측 피처를 빼고 남은 가중치를 재정규화한다.** §10.4의 `w'` 계산에서 결측 피처를 제외하면 그대로 성립하므로 별도 분기가 없다.

| 상황 | 처리 |
|---|---|
| `HRV`·`RESTING_HEART_RATE` 결측 (워치 미착용) | 두 항을 빼고 `COMPLEXION`을 남은 피처로 재정규화 → 취침 규칙성 100% |
| 취침 규칙성 이력 3일 미만 | 같은 방식으로 제외 후 재정규화 |
| `COMPLEXION` 피처가 **전부** 없음 | 그날 **혈색만** 빈 상태로 응답. `DARK_CIRCLE`·`BARRIER`는 정상 발급 |
| **단계 합(`deep+rem+core`)이 `0`** — 단계가 하나도 안 잡힌 밤 | 그날 **장벽만** 빈 상태로 응답. `DARK_CIRCLE`·`COMPLEXION`은 정상 발급 |

**대입(개인 평균·일반 기본값)을 쓰지 않는 이유는 학습 오염이다.** 채워 넣은 값으로 낸 예보가 셀피 실측과 대조되면, 존재하지 않았던 값이 개인 가중치에 반영된다. 예보 하나를 살리려고 학습 전체를 망가뜨리는 거래다.

**그 밤의 검증으로는 결측 피처의 가중치를 갱신하지 않는다.** HOME-08은 **그날 실제로 스코어링에 참여한 피처의 가중치만** 보정한다. 워치를 안 찬 밤의 오차를 `HRV` 탓으로 돌리면 안 된다.

**취침 규칙성은 최근 7일 `sleep_onset_time`의 표준편차다.** 7일은 SRI 연구의 표준 관측 창이다. **3일 미만이면 계산하지 않고 제외**한다 — 2점으로 낸 표준편차는 두 밤의 차이일 뿐 규칙성이 아니다.

> `COMPLEXION`이 셋 다 없는 경우는 **워치를 안 찬 신규 사용자**에서 실제로 발생한다. 조회 API의 빈 상태 규칙(§7 E)에 따라 200 + 상태 필드로 내보내고, 4xx로 취급하지 않는다.

#### 단계가 하나도 안 잡힌 밤

```
(deep + rem + core) == 0
    → BARRIER를 빈 상태로 (0점으로 발급하지 않는다)
```

**§10.5가 분모를 단계 합으로 잡았으므로 이건 0으로 나누는 경우이기도 하다.** 조건 하나가 두 일을 겸한다.

**0점과 결측은 다르다.** 단계 미상인 밤을 그대로 계산하면 두 피처 모두 0점 → **`BARRIER` = 0점 = "위험"** 이 나간다. 이건 *"장벽이 위험하다"* 가 아니라 *"측정하지 못했다"* 이며, 사용자에게 **없는 위험을 경고하는 것**이다.

- 워치를 차고 잤다면 단계 합이 0인 밤은 사실상 없다. **전제가 지켜지는 한 발동하지 않는다**
- **`BARRIER` 피처는 2개뿐이라 둘 다 없으면 재정규화할 대상이 0개**가 된다 — `COMPLEXION` 전멸과 같은 상황이고 같은 방식으로 처리한다
- 그 밤의 검증으로 `DEEP_SLEEP`·`REM_SLEEP` 가중치를 갱신하지 않는 것도 동일하다

> **부분적으로만 잡힌 밤은 이 조건에 걸리지 않는다** — 걸릴 필요가 없다. §10.5의 분모가 이미 측정된 구간만 보므로 비율이 자동으로 맞는다.

### 10.7 개인 가중치 보정 규칙 (HOME-08 — 2026-08-07 확정)

검증(HOME-07)이 끝나면 오차를 피처에 배분해 `personal_weight`를 갱신한다.

```
e      = 실측 − 예보                                  (지표별 오차, −100~+100)
Δw(f)  = η × (e / 100) × ((s(f) − 지표점수) / 100)
η      = 0.5                                          (고정 학습률)
w(f)   = clamp(w(f) + Δw(f), 0.5, 2.0)
```

**갱신 대상은 그날 스코어링에 실제로 참여한 피처뿐이다** (§10.6). 검증은 하루 1회이므로 학습도 하루 1회다.

#### 왜 `(s(f) − 지표점수)` 인가 — 오차를 누구 탓으로 돌릴 것인가

지표 하나당 오차는 **하나**인데 기여한 피처는 **2~3개**다. 오차를 배분할 기준이 필요하고, 그 기준이 공식에서 그대로 나온다.

지표점수는 부분점수의 가중평균이므로, 어떤 피처의 비중을 올리면 점수는 그 피처 쪽으로 끌려간다 — **정확히 `s(f) − 지표점수` 만큼**이다.

```
지표점수 = Σ (w(f)/W) × s(f)          W = Σ w(f)

∂지표점수/∂w(f) = (s(f) − 지표점수) / W      ← 비중을 조금 올렸을 때 점수가 움직이는 폭
```

그래서 오차를 줄이려면 **오차 방향 × 그 피처가 점수를 끌어당기는 방향**으로 비중을 옮기면 된다. 읽으면 이렇다:

| 상황 | 어느 피처의 비중이 올라가나 | 해석 |
|---|---|---|
| 실측이 예보보다 **나빴다** (`e < 0`) | 부분점수가 **평균보다 낮았던** 피처 | "이 사람에겐 각성이 더 치명적이더라" |
| 실측이 예보보다 **좋았다** (`e > 0`) | 부분점수가 **평균보다 높았던** 피처 | "이 사람은 깊은 수면 덕을 더 보더라" |

**초기 가중치를 균등으로 둔 결정이 여기서 한 번 더 값을 한다.** 지표 안에서 일반 가중치가 전부 같으므로 **개인 배수가 곧 상대 비중**이고, 그래서 보정식에 일반 가중치로 나누는 항이 없다. 균등이 아니었다면 지표마다 배수의 스케일이 달라져 REP-12가 보여줄 "1.7배" 같은 숫자의 의미도 지표마다 달라졌을 것이다.

#### 학습률 `0.5`의 근거는 도달 속도다

문헌이 정해줄 수 있는 값이 아니므로 **원하는 학습 속도에서 역산**했다.

> 다크서클 예보 68 / 실측 55인 밤 (`e = −13`), 각성 부분점수 50 · 총 수면 85, 지표점수 67.5
> → 각성 `1.000 → 1.011`, 총 수면 `1.000 → 0.989`
> → 비슷한 밤이 **20번** 쌓이면 `1.23` 대 `0.77` = **약 1.6배 차이**

REP-12가 예시로 든 "1.7배 민감"이 **한 달쯤 검증했을 때 자연스럽게 나오는 값**이 되도록 맞춘 것이다. 더 크면 몇 번의 우연한 오차로 가중치가 튀고, 더 작으면 해커톤 기간에 개인화가 눈에 안 보인다.

#### 상·하한 `0.5 ~ 2.0`

한 피처가 다른 피처보다 최대 **4배**까지 중요해질 수 있다. 검증 표본이 적은 초기에 우연한 오차 몇 번으로 한 피처가 지표를 지배하는 것을 막는다. **클램프가 있으므로 첫 검증부터 즉시 예보에 반영해도 안전하다** — 최소 검증 횟수를 따로 두지 않는 근거다.

#### 이 규칙에서 따라 나오는 성질

| 성질 | 내용 |
|---|---|
| **합이 0이다** | `Σ w(f) × (s(f) − 지표점수) = 0` 이므로, 한 피처가 올라가면 **반드시 다른 피처가 내려간다.** 재정규화 설계(§10.4)와 맞물린다 |
| **모르는 건 배우지 않는다** | 두 피처의 부분점수가 같으면 편차가 0이라 `Δw = 0`이다. 오차가 어느 쪽 탓인지 데이터가 말해주지 않는 날이므로 **아무것도 학습하지 않는 것이 맞다.** 버그가 아니다 |
| **상대 비중만 바뀐다** | 전체 수준은 못 바꾼다 — 아래 한계 참조 |

#### 한계 — 계통 편차는 잡지 못한다

예보가 어떤 사용자에게 **늘 15점씩 높다면**, 비중 재배분으로는 부분점수들이 만드는 범위 안에서만 내려갈 수 있다. 완전히 잡으려면 사용자별 절편(bias) 항이 필요한데, **저장할 곳이 필요하고 지금 범위 밖이다.** 넣지 않기로 한다.

> 절편을 넣지 않기로 한 것이 `personal_weight` 스키마를 지켰다. 고정 학습률이라 피처별 학습 횟수도 보정식에 들어가지 않으므로, **컬럼이 하나도 늘지 않는다** ([erd.md](erd.md) §3.7).

#### 행 생성과 부분점수 재계산

**첫 검증 때 7행을 전부 `1.0000`으로 만들고**, 그날 참여한 피처에만 보정값을 적용한다. 행 수가 항상 7로 고정되어 "행이 있다 = 개인화가 시작됐다"가 그대로 성립한다 ([erd.md](erd.md) §3.7).

보정에 필요한 `s(f)`는 **검증 시점에 `sleep_session`에서 다시 계산한다.** 검증을 마친 날의 세션은 갱신되지 않으므로(§5.1 케이스 ③) 예보 때와 같은 값이 나온다. 파생 가능한 값을 저장하지 않는다는 원칙 그대로다.

> **지표점수는 다시 계산하지 않고 `skin_forecast`에 저장된 값을 쓴다** (2026-08-10 구현 시 확정 — 그전까지 이 문단은 `s(f)`와 지표점수를 함께 재계산한다고 적고 있었다).
>
> 보정식 안에서 **`e = 실측 − 예보`의 `예보`와 `s(f) − 지표점수`의 `지표점수`는 같은 것을 가리키는 같은 항**이다. 한쪽만 다시 계산하면 두 값이 갈린다 — 저장된 값은 반올림된 정수(`68`)이고 재계산 값은 `67.5`다. 저장된 값을 쓰면 **정의상 같은 숫자**가 되고, 지표점수를 다시 만들려고 예보 산출 파이프라인을 재현할 필요도 없다.
>
> **`s(f)`와 달리 지표점수는 개인 가중치에 의존한다는 점도 있다.** 가중치는 다른 날짜의 검증으로 바뀌므로, 예보 산출과 검증 사이에 다른 날짜의 검증이 끼면 재계산 값이 산출 시점과 달라진다. 앱은 오늘 찍은 셀피만 올려 업로드와 검증이 같은 날 이어지므로 **사용자 경로에는 없고**, 며칠치를 몰아 넣고 검증을 나중에 도는 **시연 데이터 적재**에서 성립한다([api.md](api.md) §2.3이 그래서 과거 날짜를 받는다).
>
> **대가는 반올림뿐이다** — 위 예시의 보정량이 `0.0117` 대신 `0.0110`이 된다. 학습률이 도달 속도에서 역산한 값이라 이 차이는 의미를 갖지 않는다.

> ⚠️ 예외가 하나 있다. **취침 규칙성만 최근 7일 창을 쓰므로** 그 사이 과거 날짜의 세션이 갱신되면 이론적으로 `s(f)`가 어긋날 수 있다. 발생 조건이 좁고 오차도 작아 지금은 감수한다. 실제로 문제가 되면 그때 부분점수를 저장한다.

#### L1 — 가중치 산출 소스 통일

REP-07(상관 강도)과 REP-12(개인 vs 일반)가 충돌하는 것처럼 보였던 이유는 **둘이 서로 다른 질문에 답하기 때문**이다. 문구에서 이 구분을 지키면 해소된다.

| 화면 | 무엇을 말하나 | 출처 |
|---|---|---|
| REP-07 | **실제로 관측된 상관** — "당신의 데이터에서 각성과 다크서클이 함께 움직였다" | `sleep_session` × `skin_measurement` 상관계수 |
| REP-12 | **모델이 학습한 비중** — "모델은 당신에게 각성을 1.6배로 본다" | `personal_weight` (유일 출처) |
| MY-01 | **신뢰도** — 얼마나 많은 검증에 기반했나 | `COUNT(skin_measurement)` |

**둘이 다른 값을 가리켜도 모순이 아니다.** 상관은 관측이고 가중치는 학습 결과다. 다만 화면 문구가 둘을 같은 것처럼 쓰면 사용자가 혼란스러우므로, REP-12는 "모델이 본다", REP-07은 "데이터에서 나타났다"로 어투를 고정한다.
