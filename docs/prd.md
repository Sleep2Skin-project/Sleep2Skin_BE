## 1. 제품 개요

### 한 줄 정의

애플워치가 기록한 **수면 데이터를 '피부 언어'로 번역**해, 오늘의 피부 상태를 예보하고 셀피로 검증하며, 검증 결과로 개인 모델을 학습시키는 모바일 서비스.

### 핵심 가치 제안

기존 피부 앱은 "지금 피부가 어떤가"를 보여주지만, sleep2skin은 **"어젯밤 수면 때문에 오늘 피부가 어떻게 될 것인가"를 미리 알려주고, 그 예보가 맞았는지 사용자가 직접 검증**한다. 검증이 쌓일수록 예보가 개인화된다.

### 핵심 루프

```
① 수면 수집        앱이 HealthKit에서 읽어 서버로 전달 (앱 시작 시)
      ↓
② 피부 예보        수면 지표 × 개인 가중치 → 피부 지표 3종 0~100 점수
      ↓
③ 행동 처방        예보 기반으로 "오늘 할 것 / 피할 것" 추천 (TODO)
      ↓
④ 셀피 검증        5초 셀피 → LLM Vision 실측 → 예보 vs 실측 대조 → 적중률
      ↓
⑤ 개인 모델 학습    오차 방향·크기로 개인 가중치 보정 → ②의 정확도 상승
      ↓
⑥ 리포트           일간·주간·월간·종합으로 누적 패턴 제시, 필요 시 클리닉 연결
```

이 루프의 **②③④⑤가 전부 서버 로직**이며, 이 백엔드 프로젝트의 실질적 범위다.

### 피부 지표 3종 (확정)

예보(HOME-03)와 실측(HOME-06)은 HOME-07에서 1:1 대조되므로 **반드시 동일한 세트**를 사용한다.

| 한글명 | enum | 설명 | 주 영향 수면 요인 ⚠️임시 |
|---|---|---|---|
| 다크서클 | `DARK_CIRCLE` | 눈 밑 어두움 정도 | 야간 각성 횟수, 총 수면 시간 |
| 혈색 | `COMPLEXION` | 안색·혈색의 생기 | HRV·안정시 심박, 취침 규칙성 |
| 장벽 | `BARRIER` | 피부 장벽 상태 | 깊은 수면·REM 시간 |

모든 지표는 **0~100 점수**로 정규화한다. 점수가 높을수록 좋은 상태다.

> ⚠️ **지표 3종은 확정이지만, "주 영향 수면 요인" 매핑은 임시값이다.** 팀 논의로 재확정 예정. §9 참조.

## 2. 사용자 및 범위

| 항목 | 내용 |
|---|---|
| 주 사용자 | 애플워치로 수면을 기록하는 20~30대, 피부 컨디션 기복을 겪는 사람 |
| 클라이언트 | iOS 모바일 앱 (HealthKit·카메라·로컬 푸시 알림 의존) |
| 백엔드 역할 | REST API 제공. 수면 정규화, 예보 산출, 셀피 분석 중계, 개인 모델 학습, 추천 엔진, 리포트 집계 |
| 프로젝트 성격 | 해커톤 데모 (멋사 14기 중앙해커톤) — 재현성과 구현 속도를 정확도보다 우선 |
| 제외 범위 | 의료 진단. 트리아지(REP-09) 결과에는 면책 문구 고정 노출: *"의료 진단이 아닙니다. 기록 패턴에 기반한 참고 신호입니다."* |

### 확정된 기술 결정

| 항목 | 결정 | 비고 |
|---|---|---|
| 피부 지표 | 3종 — `DARK_CIRCLE` · `COMPLEXION` · `BARRIER` | 예보/실측 동일 세트 |
| 인증 | **없음** — 테스트 유저를 DB에 직접 주입 | 해커톤 범위. 로그인 화면 없음 |
| DB | MySQL + Spring Data JPA | |
| LLM Vision | OpenAI `gpt-5.6-terra` (Responses API + Structured Outputs) | 프로퍼티로 모델 교체 가능 |
| 이미지 임시 저장 | AWS S3 (Lifecycle 1일 자동 만료 + 분석 직후 즉시 삭제) | §5 참조 |
| HealthKit 수집 | **앱이 읽어 서버로 전달** (서버 배치 아님) | 앱 시작 시 업로드 → 즉시 스코어링 |
| 배포 | AWS EC2 + Docker + CI/CD 파이프라인 | |

### 셀피 이미지 취급 정책 (제품 정체성)

셀피는 **분석 직후 즉시 삭제**하며, 얼굴을 복원할 수 있는 어떤 데이터도 보관하지 않는다. 지표 3종의 숫자만 DB에 남는다. 이 정책은 온보딩(ONB-04)에서 고지되고 마이페이지(MY-04)에서 실제 실행 지점을 제공하는, **마케팅 문구가 아니라 구현 제약**이다.

> ⚠️ **정확한 표현 주의**: S3를 경유하므로 이미지가 인프라에 잠시 존재한다. 따라서 "저장하지 않습니다"가 아니라 **"분석 직후 즉시 삭제하며, 얼굴을 복원할 수 있는 데이터를 보관하지 않습니다"**로 표현해야 한다. 이를 뒷받침하는 구현은 §5 참조.

## 3. 정보 구조

```
[HOME] [TODO] [REPORT] [MY]          ← 하단 탭 네비게이션
※ 온보딩(ONB-01~05)은 탭 밖 진입 플로우
```

### 온보딩 플로우

```
시작 화면(ONB-01)
   ↓
개인정보 동의(ONB-02) ──no──→ 앱 종료
   │ yes
   ↓
수면 데이터 연결(ONB-03) ──yes/no 모두──→ 랜딩 HOME(ONB-05)
```

> 미연결 사용자도 HOME에 진입하므로 **HOME-02·HOME-03의 빈 상태 처리가 필수**다. (§7 참조)

### 화면 도메인 ↔ 백엔드 패키지 매핑

화면 도메인과 백엔드 데이터 도메인은 1:1이 아니다. HOME 화면 하나가 수면·피부 두 데이터 도메인을 걸친다.

| 화면 도메인 | 백엔드 패키지 | 근거 |
|---|---|---|
| ONBOARDING | `user` | 동의 이력, 온보딩 완료 상태 |
| HOME | `sleep` + `skin` | 수면 통역(HOME-02)은 sleep, 예보·검증·학습(HOME-03/06/07/08)은 skin |
| TODO | `todo` | 추천 엔진, 체크리스트 |
| REPORT | `report` | 집계·분석 전용 (sleep·skin 조회) |
| MY | `user` | 프로필, 데이터 관리 |

상세는 [architecture.md](architecture.md) 참조.

## 4. 기능 명세

우선순위: `high` = MVP 필수 / `medium` = 데모 품질 향상 / `low` = 후순위
난이도: 명세서의 개발 난이도(상·중·하)
BE: 서버 작업 유무 — **`—` 표시는 클라이언트 전용, 백엔드 구현 대상 아님**

### 4.1 온보딩 (ONB)

| ID | 기능명 | 우선 | 난이도 | 백엔드 처리 |
|---|---|---|---|---|
| ONB-01 | 앱 시작 화면 (가치 제안) | high | 하 | — (로컬 온보딩 완료 플래그만 확인) |
| ONB-02 | 개인정보 수집·이용 동의 (분기) | high | 하 | 동의 이력 저장(약관 버전·동의 시각·사용자 식별자) |
| ONB-03 | 수면 데이터 연결 (HealthKit) | high | 중 | **앱이 전달한 수면 세션 수신 → 정규화 → DB 저장** |
| ONB-04 | 프라이버시 고지 (셀피 미저장) | high | 하 | — (정적 화면) |
| ONB-05 | 랜딩 진입 및 온보딩 완료 처리 | high | 하 | 온보딩 완료 상태 및 초기 설정 저장 |

> **ONB-03 난이도 하향** (상→중): 서버가 HealthKit에 직접 접근하지 않고 앱이 읽어 전달하는 구조로 확정되어, 서버는 수신·정규화·저장만 담당한다.

**수집 데이터 4종** (앱이 HealthKit에서 읽기 전용으로 취득 후 전달):

| 수면 데이터 | 피부 측면의 의미 | 연결 지표 ⚠️임시 |
|---|---|---|
| ① 깊은 수면·REM·코어 (분) | 장벽 재생 / 콜라겐 지표 | `BARRIER` |
| ② 취침·기상 시각 | 수면 규칙성 | `COMPLEXION` |
| ③ 야간 각성 횟수 | **다크서클 예측의 핵심 변수** | `DARK_CIRCLE` |
| ④ HRV · 안정시 심박 | 스트레스성 트러블 신호 | `COMPLEXION` |

> 수집 데이터 4종은 확정이나 **연결 지표 매핑은 임시값**이다. §9 참조.

### 4.2 HOME — 예보와 검증

| ID | 기능명 | 우선 | 난이도 | 백엔드 처리 |
|---|---|---|---|---|
| HOME-01 | 날짜 및 웰컴 멘트 | high | 하 | — (클라이언트 로컬 시각) |
| HOME-02 | 어젯밤 수면 통역 카드 | high | 중 | 수면 세션 정규화 → 기준치 대비 편차 → 가장 부족한 지표 1개 선정 → 헤드라인 템플릿 주입 |
| HOME-03 | **오늘의 피부 예보** | high | **상** | 수면 지표 가중합 스코어링 → 개인 가중치 반영 → 0~100 정규화 → 등급 컷오프 → 오늘자 예보 저장 |
| HOME-04 | 게이미피케이션 (캐릭터·레벨·EXP) | low | 중 | **방향 미확정** — EXP 적립 트리거·레벨 테이블 미정 |
| HOME-05 | 셀피 검증 — 촬영 | high | 중 | — (촬영 단계 서버 전송 없음, 갤러리 저장 안 함) |
| HOME-06 | 셀피 검증 — 분석 (LLM Vision) | high | **상** | S3 임시 업로드 → OpenAI Vision 분석 → 0~100 정규화 → 지표 저장 → **원본 즉시 삭제** |
| HOME-07 | 셀피 검증 — 결과 (예보 vs 실측) | high | 중 | 지표별 \|예보−실측\| → 판정 매핑(적중/근접/과소예측/과대예측) → 적중률 → 이력·연속일수 갱신 → HOME-08 학습 트리거 |
| HOME-08 | 개인 모델 학습 (가중치 보정) | medium | **상** | 오차 방향·크기 반영해 개인 가중치 업데이트(단순 평균 이동) → 다음 예보에 즉시 적용 → 변화 설명 문장 생성 |
| HOME-09 | 예보 적중률 · 연속 검증 배너 | medium | 하 | 최근 검증 1건 조회 + 연속일수 계산 |

**HOME-03 → HOME-07 연결**: HOME-03이 저장한 오늘자 예보값이 HOME-07 대조의 기준이 된다. 예보 산출 없이는 검증이 성립하지 않는다.

**셀피 검증 서브플로우**: `HOME-05 촬영 → HOME-06 분석(자동 전환) → HOME-07 결과 → "오늘의 스킨 처방" → TODO 탭`

**TODO-07 예시 출력**: `23:40 취침 → 장벽 78·회복` vs `02:00 취침 → 장벽 45·악화`, 밤 체크리스트 3항목(카페인 컷오프 15:00 / 취침 30분 전 화면 끄기 / 침실 온도 19–21℃), 상태 3종(통과 / 알림 예약 / 미확인).

### 5.1 수면 데이터 수신 (HealthKit)

서버는 HealthKit에 직접 접근할 수 없다. 앱이 권한을 얻어 읽은 데이터를 서버로 전달한다.

```
[앱 시작]
  → 앱이 HealthKit에서 지난밤 수면 세션 읽기
  → POST /api/v1/sleep/sessions  (수면 세션 페이로드)
  → 서버: [중복 판단] → 정규화 → 저장 → 즉시 스코어링(HOME-03) → 예보 응답
  → 앱: HOME 화면에 예보 표시
```

이 구조의 결과:
- **서버 스케줄러가 필요 없다.** 배치 인프라와 실패 재시도 설계가 통째로 사라진다.
- HealthKit 단계 구분이 기기·OS 버전별로 다를 수 있으므로 **앱↔서버 간 수면 단계 매핑 규칙을 계약으로 고정**해야 한다.

#### 중복 수신 차단 (필수)

앱이 시작될 때마다 업로드하므로, **새 수면 데이터가 생기기 전까지는 같은 세션이 반복 전송된다.** 하루에 앱을 다섯 번 켜면 같은 데이터가 다섯 번 온다.

이때 **처리를 시작하기 전에 중복을 판단해 되돌린다.** 저장 후 덮어쓰는 upsert가 아니라, **아예 처리하지 않는다.**

```
POST /api/v1/sleep/sessions 수신
  │
  ├─ 페이로드 정규화 → 내용 해시 계산            ← 저장 전에 수행
  │
  ├─ (user_id, sleep_date)로 기존 세션 조회
  │
  ├─ ① 기존 없음        → 저장 + 스코어링 + 예보 산출    → 201 Created
  ├─ ② 기존 있음·해시 동일 → 아무것도 하지 않음
  │                       → 기존 예보를 그대로 반환      → 200 OK
  └─ ③ 기존 있음·해시 다름 → 그날 검증을 마쳤는가?
                             ├ 검증 완료 → 갱신하지 않음. 기존 예보 반환 (processed=false)
                             └ 검증 전   → 갱신 + 재산출        (processed=true)
```

**②에서 재처리를 막아야 하는 이유** — 단순한 성능 문제가 아니다:

| 이유 | 설명 |
|---|---|
| **검증 무효화 방지** | 예보를 다시 산출하면 오늘자 예보값이 바뀐다. 이미 셀피 검증(HOME-07)을 마쳤다면 **대조 기준이 사후에 바뀌어 적중률이 조작된 셈**이 된다 |
| 학습 오염 방지 | 재산출이 개인 가중치 학습(HOME-08)을 다시 트리거하면 같은 데이터로 여러 번 학습해 가중치가 왜곡된다 |
| 비용 | 스코어링·집계가 무의미하게 반복된다 |

**응답에 처리 여부를 명시한다.** 앱이 "새 예보인지 기존 예보인지"를 알아야 화면 갱신 여부를 판단할 수 있다.

```json
{ "success": true, "data": { "processed": false, "forecast": { ... } }, "error": null }
```

**구현 요건**:
- `SleepSession`에 `payload_hash` 컬럼(정규화된 페이로드의 SHA-256)을 둔다
- `(user_id, sleep_date)`에 유니크 제약을 걸어 DB 레벨에서도 중복을 막는다
- 해시 계산은 **정규화 후** 수행한다. 앱이 필드 순서를 바꿔 보내도 같은 데이터로 판정되어야 한다

### 5.2 셀피 이미지 파이프라인 (S3)

"얼굴 데이터를 보관하지 않는다"를 **설명이 아니라 구조로 증명**하는 것이 목표다.

```
[앱] 셀피 촬영 (갤러리 저장 안 함)
  → 서버에 업로드
  → 서버: S3에 임시 저장 (키: selfie/tmp/{uuid}.jpg)
  → OpenAI Vision 호출 → 지표 3종 0~100 산출
  → S3 객체 즉시 삭제 (finally 블록에서 보장)
  → DB에 숫자 지표 3개만 저장
  → 앱에 결과 반환
```

**보관하지 않음을 뒷받침하는 4가지 구현 장치**:

| # | 장치 | 목적 |
|---|---|---|
| 1 | **S3 Lifecycle 정책 — `selfie/tmp/` 접두사 1일 후 자동 만료** | 서버 장애로 삭제 코드가 실행되지 못해도 잔존을 막는 안전망 |
| 2 | **`finally` 블록에서 삭제** | 분석 실패·타임아웃·예외 발생 시에도 삭제 보장 |
| 3 | **DB 스키마에 이미지 경로/URL 컬럼을 두지 않음** | 애초에 이미지를 참조할 방법이 없다. 스키마 자체가 정책의 증거 |
| 4 | **버킷 퍼블릭 액세스 전면 차단 + 서버 IAM 역할로만 접근** | 임시 존재 구간에도 외부 노출 불가 |

**확인이 필요한 항목**:
- OpenAI API의 데이터 보관 정책 — 요청 로그에 이미지가 남는지, zero data retention 적용 가능한지 확인 후 사용자 고지 문구를 확정해야 한다. (§7 참조)
- 원본을 S3에 올리지 않고 요청 본문에 바로 실어 보내는 방식도 가능하다. 그러면 우리 인프라에는 이미지가 전혀 남지 않아 설명이 더 단순해진다. **S3 경유가 꼭 필요한지 재검토 여지가 있다.**

## 9. 임시값 목록 (재확정 예정)

아래 값들은 **문서를 완성하기 위해 임시로 채워 넣은 것**이며, 팀 논의로 재확정한다. 확정 전까지는 코드에 하드코딩하지 말고 **설정값 또는 상수 클래스 한 곳에 모아** 나중에 한 번에 교체할 수 있게 한다.

### 9.1 수면 피처 → 피부 지표 매핑 ⚠️임시

리포트(REP-07)와 예보 산출(HOME-03) 양쪽에서 쓰인다. **이 매핑이 바뀌면 예보·리포트·학습이 전부 바뀐다.**

| 수면 피처 | → 지표 | 근거 상태 |
|---|---|---|
| 야간 각성 횟수 | `DARK_CIRCLE` | 원 명세 유지 — 비교적 신뢰 |
| 깊은 수면 시간 | `BARRIER` | 원 명세 유지 — 비교적 신뢰 |
| 총 수면 시간 | `DARK_CIRCLE` | **임시** — 원래 유분에 연결, 유분 제외로 재배치 |
| 취침 규칙성 | `COMPLEXION` | **임시** — 원 명세의 "톤"을 혈색으로 대체 |
| HRV · 안정시 심박 | `COMPLEXION` | **임시** — 원 명세에 쌍 없음. 수집 데이터 4종에 있어 신규 추가 |

논의가 필요한 지점:
- `COMPLEXION`에 2개 피처가 몰려 있고 `BARRIER`에는 1개뿐이다. 균형이 맞는지 검토 필요
- `DARK_CIRCLE`에 야간 각성과 총 수면 시간이 둘 다 붙어 있어 상관이 중복 계산될 수 있다
- 지표당 피처 개수가 다르면 가중합 정규화 방식도 지표별로 달라져야 한다

### 9.2 그 밖의 임시값

| 항목 | 현재 상태 | 확정 시점 |
|---|---|---|
| 가중합 스코어링 공식·초기 가중치 | 미정 (§7 **B1**) | HOME-03 구현 직전 |
| 등급 컷오프 구간 | 미정 (§7 **B2**) | HOME-03 구현 직전 |
| 판정 오차 구간 | 미정 (§7 **B3**) | HOME-07 구현 직전 |
| 상관 강도 라벨 4단계 계수 구간 | 미정 (§7 L7) | REP-07 구현 직전 |
| 모델 신뢰도 등급 일수 구간 | 미정 (§7 L8) | MY-01 구현 직전 |
| 트리아지 발동 임계값 | 미정 (§7 L6) | REP-09 구현 직전 |
| 수면 목표값 (깊은수면 분·취침 시각) | 미정 (§7 **B6**) | REP-02 구현 직전 |

### 9.3 구현 시 지킬 것

임시값이 코드 곳곳에 흩어지면 재확정 때 전부 찾아다녀야 한다. **한 곳에 모은다.**

```java
// domain/skin/ScoringPolicy.java — 임시값 전용. 확정 시 이 파일만 고친다
public final class ScoringPolicy {
    // ⚠️ 임시값 — PRD §9.1. 팀 논의로 재확정 예정
    public static final Map<SleepFeature, SkinMetric> FEATURE_METRIC_MAP = ...;
    // ⚠️ 임시값 — PRD §9.2
    public static final int GRADE_CUTOFF_GOOD = 70;
    ...
}
```

임시값을 참조하는 코드에는 주석으로 출처를 남긴다: `// 임시값 (PRD §9.1)`
